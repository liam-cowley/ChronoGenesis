# ChronoGenesis — notes for AI coding sessions

Minecraft **1.21.1**, **NeoForge 21.1.x**, ModDevGradle, Java 21, Mojang mappings + Parchment.
Mod id `chronogenesis`, base package `com.chronogenesis`. Design: temporal essence harvested from
living beings powers rituals and grows biomechanical multiblocks, culminating in a BioComputer
that unlocks travel to past eras (and finally an Elder God boss). Witchery/Botania-like feel,
explicitly NOT an industrial/tech mod; progression should branch, not be linear.

Mood: gloomy mad scientist, but still Minecraft (the player should feel like a mad scientist the way
Witchery made you feel like a witch). Tools are improvised from vanilla materials (copper, glass,
clocks, candles, amethyst, lightning rods); machines are *grown* over brass frames and jolted alive
with lightning, never assembled from gears/plates. Gore stays at vanilla rotten-flesh level.

Docs (read the relevant one before implementing a feature, and keep names consistent with it):
- `docs/design/core-systems.md`: source of truth for essences, grown organisms/grafts, veins, powers,
  time manipulation, the Chronocortex, the Temporal Lens and structures.
- `docs/design/early-game.md`: pacing, and the build order with what is done (✅) and what is next (⬜).
- `docs/tech-stack.md`: versions, libraries, run configurations, CI, tools.
- `docs/assets/texture-catalogue.md`: every texture, what it is, and how layered textures fit together.

## Hard rules: use the 1.21.1 APIs, not older Forge or newer (1.21.2+/26.x) ones
- Registration: `DeferredRegister.createBlocks/createItems` -> `DeferredBlock`/`DeferredItem`; other registries via
  `DeferredRegister.create(Registries.X, MODID)`. Never use `RegistryObject` or `ForgeRegistries` (old Forge).
- Item stack data uses **Data Components** (`DataComponentType`, registered on `Registries.DATA_COMPONENT_TYPE`), not NBT tags.
- Entity/BE/chunk/level extra data uses **Data Attachments** (`ModAttachments`), not capabilities-as-storage.
  Capabilities in 1.21.1 are only for exposing handlers (`RegisterCapabilitiesEvent`, `Capabilities.ItemHandler.BLOCK`).
- `ResourceLocation.fromNamespaceAndPath(...)` / `ChronoGenesis.id(path)`; `new ResourceLocation(...)` no longer exists.
- Networking: `RegisterPayloadHandlersEvent` + `CustomPacketPayload` records with `StreamCodec`.
- Loot tables live in `data/<ns>/loot_table/` (singular), recipes in `data/<ns>/recipe/`, tags in `data/<ns>/tags/block/` etc.
- Item models are the classic `models/item/*.json` (the 1.21.4 `items/` client item format does NOT apply).
- `@EventBusSubscriber(modid = ChronoGenesis.MODID)` auto-routes mod-bus vs game-bus events; no `bus =` needed.
- Datagen uses `GatherDataEvent` (single event, `includeClient()`/`includeServer()`), `BlockStateProvider`, `ItemModelProvider`.

## Conventions
- One registry class per type in `registry/` (`ModBlocks`, `ModItems`, `ModBlockEntities`, `ModEntities`,
  `ModDataComponents`, `ModAttachments`, `ModRecipes`, `ModMenus`, `ModSounds`, `ModParticles`...), registered in the
  `ChronoGenesis` constructor. Keep the main class free of gameplay logic.
- Planned feature packages: `essence/` (extraction, storage, transfer), `ritual/`, `biomech/` (multiblock growth),
  `biocomputer/`, `timetravel/` (era dimensions), `world/` (worldgen per era), `entity/`, `client/` (renderers, screens;
  client-only code ONLY here or in `ChronoGenesisClient`).
- Every new item/block needs: model/blockstate in datagen, lang entry in `ModLanguageProvider`, loot table for blocks,
  a texture in `src/main/resources/assets/chronogenesis/textures/`. Run `gradlew runData` afterwards.
- `src/generated/resources` is datagen output: change the providers, not the JSON.
- Prefer JSON data (recipes, ritual definitions, multiblock patterns via custom datapack registries) over hard-coded
  Java so content is tweakable by packs.
- Test both `runClient` and `runServer` before calling a feature done.

## CI and tooling
- `.github/workflows/build.yml` compiles every push and runs the game tests. `datagen.yml` (feature branches) runs `runData`, **commits
  `src/generated/resources` back to the branch**, then boots a dedicated server as a smoke test; problems show up
  as workflow annotations. Pull after pushing before editing generated files' sources again.
- Textures are generated by `tools/textures.py src/main/resources/assets/chronogenesis/textures [preview.png]`
  (16x16 pixel art, hand-placed grids). Art direction: Frankenstein (stitches, staples, electrodes, jars) +
  Call of Cthulhu (eyes, maws, tentacles, eldritch green) + steampunk (brass, copper, rivets, valves).
  Edit the script and re-run rather than hand-editing PNGs, unless replacing a texture with real art for good.
- Post-processing shaders live in `assets/chronogenesis/shaders/` (post chain + program JSON + `.fsh`), run from
  client code with a `PostChain` (see `client/LensView`: render into a chain target during the world render at
  `AFTER_WEATHER`, composite from a HUD layer the way vanilla's blur does; `AFTER_LEVEL` has no camera matrices). They must compile under GL 3.2 core
  (`#version 150`); a shader that fails to load disables its effect instead of crashing.
- The past is a real dimension (`chronogenesis:past`, `timetravel/PastDimension`): overworld generator and seed,
  ruins stamped with their past templates. The Temporal Lens shows it by streaming its chunk sections to the
  client (`lens/LensSync`, `client/PastSections`/`PastMesh`). The game-test server only builds the flat preset's
  dimensions, so tests cannot load it; they check its files decode and run stamping on the test world.
- The creative-only Eternal Hourglass keeps essences full and instruments charged while carried, and pays the essence
  of Chronocortex research (no wired organisms needed): use it to test.
  Using it in creative mode (or `/chronogenesis journal unlock`) grants every ChronoGenesis advancement, which
  unlocks the whole journal. A creative-only Chronocortex item places an awake cortex without the ritual.
- `tools/make_structures.py` writes the worldgen structure templates. Each ruin is generated from its "past"
  template by seeded decay, so the Temporal Lens's past view lines up with it block for block. Edit the layout
  there and re-run; never hand-edit the NBT.
- `tools/render_models.py <out.png>` renders isometric previews of the generated block models (pull the
  datagen commit first). Use it to check model changes without launching the game.
- Organism models are built in `ModBlockStateProvider` from shared parts (brass frame, tinted flesh masses,
  untinted brass/eyes). Flesh has `growth` 0-3 (tendrils, creeping, swelling, mature); cores have `phase`
  (seed, awake, hungry, necrotic). Keep new organism blocks in the same style.
- Grafts have an `active` blockstate for visible work (the Leech Tendril swells as it gulps); give a graft an
  active model with `graftBlock(block, model, activeModel)`. Leeching is shown with `EssenceMoteOptions` particles
  (client: `EssenceMoteParticle`), which home in on a target point.
- Layered textures: containers = `<name>` + `<name>_fill` (tinted by aspect, layer 1) + `<name>_front`;
  culture = `culture` (tinted) + `culture_dish`; flesh/core = `<name>` (tinted) + `<name>_overlay`.
- Hand-written data (recipes, tags, loot modifiers, data maps, advancements, Patchouli journal) lives in
  `src/main/resources`; models, blockstates, lang and block loot tables are datagen.
